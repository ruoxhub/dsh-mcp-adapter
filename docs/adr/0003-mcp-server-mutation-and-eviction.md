# MCP 服务器变更完整性与运行时驱逐 (Server Mutation & Eviction)

Context: 在 Web UI 面板对 MCP 服务器进行编辑和删除时，若仅对磁盘上的 JSON 配置文件进行简单键值修改，会引发三类不一致问题：
1. **改名残留**：修改服务器名称时，若仅将新键写入配置文件，旧键仍会残留在 `mcpServers` 中，导致配置被隐式复制而非改名；
2. **跨作用域孤儿**：在“电脑 用户”（全局）与“工作区”（本地 `.mcp.json`）之间迁移配置时，若未清理原作用域配置，会在两处同时存在；
3. **运行时脱节**：常驻进程池 `ServerPool` 与工具目录缓存未收到通知，已启动的旧 stdio 子进程继续运行，模型仍感知旧工具定义直到重启或空闲超时。

Decision: 我们决定：

1. **原子保存与迁移（Atomic Save & Migration）**：`saveServer` 接口支持传入 `originalName` 与 `originalScope`。当检测到名称重命名或作用域发生切换时，在新作用域与新名称成功落盘后，立即从原配置文件中清理旧条目，并作废或清理旧的审批哈希记录。
2. **运行时进程池与目录双驱逐（Pool Eviction & Cache Invalidation）**：在执行 `deleteServer` 或包含连接参数变动的 `saveServer` 时，通过服务挂载的清理回调主动驱逐 `ServerPool` 中对应常驻连接/子进程，并同步清除磁盘与内存中的工具目录缓存条目。
3. **卡片内联操作与安全确认**：Web UI 列表卡片直接平铺 `[测试连接]`、`[编辑]`、`[删除]` 操作入口，破坏性删除操作在前端保留确认提示，并提供实时错误与反馈展示。

Status: accepted

Considered Options:

- 选项 A：不做原名与原作用域关联，将改名视为“新建”，由用户自行前往旧作用域手动删除。缺点是用户体验断裂且极易在配置文件中遗留大量无效孤儿服务。
- 选项 B（采纳）：在保存接口显式声明源身份，后端保证原子写入与清理；同时打通服务层到进程池与缓存层的驱逐通知。
- 选项 C：不主动断开连接，依赖超时自然退出（idle timeout 30s）。缺点是当用户修改了错误的命令或参数时，由于旧进程存活，无法立即进行修复验证，排错延迟高。

Consequences:

- `McpServersService` 需要可选接收 `ServerPool` 实例或驱逐回调函数。在独立测试场景下可缺省降级，在完整插件挂载时建立联动。
- 前端 `ServerEditorTab` 在编辑模式保存时需提取并提交 `editingServer` 的原始 `name` 和 `scope`。
